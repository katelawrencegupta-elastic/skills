# Diagnostic Serverless consolidation

Quote Serverless from diagnostic measurements. The K360 account summary is a different skill (`k360-account-analysis`). Reuse its org report. Do not rerun that summary.

A fast model launches the one command below and writes the chat bullets from the printed brief. A stronger model continues in that same thread when an echo or E73 gate fails, a solution is split by region, or the user asks for the 2–5 project pack. One run. The sheets and the search-power model run inside the command.

## Hard rules
1. **Observability and Security ingest are diagnostic bulk.** Bulk is measured on the primary shards after ingest pipelines and before compression, which is what the estimators call metered ingest. So it is written as metered: Observability through Option 1 (G19 logs and traces, G20 TSDS metrics, each GB/day × 730 ÷ 24, with the raw-data rows at 0), and Security as G4 = bulk ÷ the sheet's own expansion factor (1.66), so G5 comes back as the bulk. No expansion factor is applied to bulk. The K360 backup keeps the raw-data cells. Daily GB is `bulk_gb_day`. Retention is `retention_days`, and only a value above 0 enters the weight. A row with no measured age is named and left out. Stored GB, stored GB ÷ months, and node size ÷ uptime are not this ingest. Search disk is local store. Search ingest docs/s is the K360 org rate × the billing-window usage factor (`ecu.quote_usage_factor`), times local search store ÷ org store. On one region, query rate stays the org window. When Search is split by region, query rate is scaled by that region's share of search store. Say so when quoting Search.
2. **The estimator read-back is the dollar.** Observability monthly is D38. Security monthly is E74 up to 12 months of retention, and the sheet's month 36 above that, because E74 is month 12 and retained GB is still filling then. Search is the es3 performant profile. The ladder is a check. Never edit a golden template.
3. **Match the estimator to the solution.** Observability on the Observability sheet, Security on the Security sheet, Search on es3.
4. **The month written is a whole number.** Snap a remainder under 0.001 month down, round up, then clamp to 1–36. 365 days writes 12. The run writes one consolidation PDF, at that rounded month. Each solution with a workload gets one estimate sheet per region. A solution with no workload is skipped. There is no 30-day read: no second PDF, no `_30d` sheets, and no `thirty_day` in the brief. Estimate sheets go directly in `generated_estimates`. Plan sheets stay in `generated_estimates/plan_sheets`. The consolidation PDF, the appendix, and the account PDF are in the run folder root. There are no `full_retention` or `30d` folders. An estimate or a consolidation PDF that an earlier run filed under a `full_retention` or `30d` folder is moved up, on disk and on Drive, and the folder is removed once it is empty. An estimate sheet is named `<customer>_<date>_<solution>_full retention_<bulk|k360>_<region>_serverless_estimate`. The region is the cloud region that sheet was scoped to. A solution that spans regions is one sheet per region, and only when that region's projected sizing is more than $10/mo. Observability and Security project from that region's bulk and retention. Search projects that region's share of the solution ballpark. A region at or under $10/mo is left out of the quote. There is no second fleet-wide sheet for that solution. Search disk is the measured local store and is never scaled by a retention month.
5. **Size the last 90 billed days.** The quote window is three months (`--lookback-days`, default 90). A deployment is in the quote when it has billing ECU in that window. The window ends on the last day with a positive total. A partial calendar month is not the window. A deployment with no bill in those 90 days is out, including its last snapshot. An active deployment with no bundle is not sized: it adds no ingest and no stored GB, and with the default scope its bill is not in the ECH figure either. An org with fewer billed days than the window is priced on the days it has, and the brief says so. A week-grain org report (written by `run_org_report.py`) has no daily series and stops the run: do not `--reuse` one. An org report fetched before 90-day rosters were saved carries only a 30-day roster, so the 90-day roster is rebuilt from its daily and monthly series; fetch again for the exact set.
6. **One estimate per title.** There is exactly one sheet per solution × region. The title carries both. Reusing a title updates that sheet. `--fresh` replaces it and trashes the earlier copy. The run ends with a dedupe pass that trashes every older same-titled sheet anywhere under the run folder. `size_serverless.py --account-json <diags_account.json> --dedupe --dedupe-dry-run` lists what it would trash. Plan sheets are the same: one per title.
7. **Read the printed brief only.** The command prints `brief <path>`. That file is `<run_key>_consolidation_brief.json`. Do not open `*_account.json`, `*_diags_account.json`, the org report, infra, `sizing.json`, `calculations.md`, `canvas-layout.md`, or `render_pdf.py`. The PDF is the full report. When Chrome is missing, the HTML file in `links` is the report.

## Run
`<skill>` is the directory that contains this file. The same directory works for Claude and Cursor.

```bash
cd <project with .env>          # KIBANA_URL, ELASTIC_API_KEY, FOUND_ADMIN_API_KEY

# Reuse the account-summary fetch when that folder already exists.
python <skill>/scripts/run_consolidation.py --org "ORG NAME" \
  --reuse serverless_analyzer/diag_artifacts/<customer>_<date>/<customer>_<date>_org_report.json

# Bundles already on disk. Does not call the admin API.
python <skill>/scripts/run_consolidation.py --org "ORG NAME" \
  --reuse serverless_analyzer/diag_artifacts/<customer>_<date>/<customer>_<date>_org_report.json \
  --diags-dir serverless_analyzer/diag_artifacts/<org_id>_diags_<date>

# Several cloud orgs share the customer name. Pass every id.
# The contract pivot is the id with the highest commit. Billing, storage,
# workload, and diagnostic bundles cover every id.
python <skill>/scripts/run_consolidation.py --org "ORG NAME" \
  --org-id ID1 --org-id ID2 --org-id ID3
```
**Leave deployments out.** `--exclude-deployment <deployment id>` (repeat, or comma list; 32 hex characters) removes a deployment from everything: billing ECU and so the ECH bill on page 1, diagnostic bulk, stored GB, the deployment count, the plan ceiling, and every estimate. Ids resolve through `manifest.json` in `--diags-dir`, else the admin deployment list; an id that matches nothing stops the run. Billing is monthly per deployment, so the ECU removed from each day is that deployment's share of its month's org ECU. The run key gains `_excluding_<n>` so an excluded run never overwrites the full-fleet folder or sheets. Page 1 and the brief (`excluded_deployments`) name what was left out.

**Monitoring clusters are left out by default.** A deployment whose name has `monitoring` as a name part (`monitoring`, `prod-monitoring`, `ES_Monitoring_01`; not `monitor` or `monitoringx`) holds other clusters' stack-monitoring data and is not a workload that moves to serverless. A consolidation run excludes it exactly as `--exclude-deployment` does (billing ECU, bundle, stored GB, counts, plan, estimates), resolves its id through `manifest.json` or the admin list, and adds `_excluding_<n>` to the run key. If no id resolves it is still removed by name and a warning says its bundle on disk is not skipped. Pass `--keep-monitoring` to include it. The account summary (`run_account_analysis.py`) does not exclude it. The brief (`excluded_deployments`) names each one with `reason: monitoring cluster`.

**Complete diagnostics.** Every download is checked as a whole zip (CRC, and length when the server sends it). A failed or cut-short capture is retried three times, then once more on its own after the rest finish. Bundles already on disk are checked too, and a bad one is fetched again. If a deployment still has no bundle the run stops and names it. `--allow-missing-diags` continues without it: page 1 then says which active deployments were not measured and that their ingest is not in the estimate (`diagnostics_coverage.download_failed`, `fallback_names`).

Do not pass `--skip-diags`, `--skip-sizing`, or `--k360-ingest` unless the user asked for the K360 backup as a separate document. Diagnostics are the quote. A fresh admin pull checks TLS to the pinned admin host before it sends the API key. Connect the Aviatrix VPN tunnel when that check fails. `--xlsx` is off unless the user asked for local workbooks. Pass `--skip-deployment-plan` only when the user asked to skip the bars.

**What is compared.** Four flags set the ECH side of the comparison and what happens to a deployment that could not be measured. Leave them at their defaults unless the user asks.
- `--ech-scope priced` (default) compares only the deployments that got a serverless price: a matched bundle, and a solution whose read-back was accepted. Everything else is named on page 1 as not compared, with its $/mo: deployments with no price, existing serverless projects, and lines with no deployment on the roster. `--ech-scope all` compares the whole billing window, less existing serverless projects. Page 1 then says the change is overstated by the unpriced deployments' bill.
- `--unmeasured exclude` (default) leaves an active deployment with no bundle off both sides. `--unmeasured k360` prices it from K360 stored GB ÷ `--retention-months` × the estimator's expansion, labels it `k360_fallback`, and keeps Bundle coverage flagged. `--unmeasured fail` stops the run and names them. A decommissioned deployment is never priced.
- `--min-priced-ecu-pct N` (default 90) is the bar on the `Priced share` integrity check: priced deployments' billed cost ÷ every ECH deployment's billed cost in the window.
- `--keep-serverless-spend` leaves existing serverless projects' cost in the ECH figure. It only matters with `--ech-scope all`.

`--lookback-days` defaults to 90 and cannot exceed 365. That window sets the ECH month and the roster of active deployments. It does not change the GB/day written into the estimators, which is diagnostic bulk as measured. The account summary still fetches the trailing year. Pass `--lookback-days 365` for a year, or `--lookback-days 30` for the last month only. A value outside 1–365 stops the run.

## After the script
Quote only when `ingest_source` is `diagnostics`. Build `<slug>-serverless-consolidation-savings.canvas.tsx` from the brief: `savings`, `quotes`, `fleet`, `contract_rate`, `ech_scope`, `notes`, `diagnostics_coverage`, `deployment_plan`, `metered_rates`, `search_power`, `integrity`, `estimators`, `method`, and `links`. `method` is the commit and the rules that produced the run; two runs of one customer are comparable only when it matches, and `uncommitted_changes: true` means the scripts had edits no commit records. Chat is at most six bullets plus those links. Use the HTML path when a link has no PDF.

**Cover.** Page 1 is the last 90 days of billed cost unless `--lookback-days` says otherwise. The chart title names that window: the total of those billed days, expressed as a month (that total ÷ the number of days × 30.416). ECH dollars are the K360 billing `cost` field, summed as billed: that field is the ECU total and 1 ECU is $1. No ARR ÷ (commit × 365) rate is applied to it, on any page. `contract_rate` in the brief carries ARR and commit for reference only, with `implied_usd_per_ecu` null and `basis` `k360_cost`. The page 1 chart draws that ECH billed cost and serverless at list. The page 1 reduction is ECH billed cost minus serverless at list. The deployment-count chart draws serverless at list and the ECH bill on every step. The amount under the project count is that ECH bill minus serverless at list. Serverless is not discounted anywhere in the report. `savings` in the brief is `ech_list_mo` (ECH billed cost for the month), `serverless_mo`, and their difference `list_mo`, `list_yr`, `list_pct`; a negative difference is an increase. The estimators are filled with diagnostic bulk as measured. The billing window sets the ECH month and does not scale bulk (`ecu.quote_ingest_factor` is 1.0), because bulk is a rate measured when the bundle was captured. Only the K360 backup scales its stored-GB ingest by that pace. `savings` is that read-back. The first row under “What if data is kept longer, or the fleet is busier” is the same window. The complete-month average and the quietest month scale that read-back and are not re-estimated.

**Increase, not reduction.** When serverless at list is above the ECH billed cost, the two change boxes read "Estimated monthly increase" and "Estimated increase" versus ECH billed cost, show the amount without a minus sign, point the arrow up, and use the danger colour. The headline and the cover notes say increase. A saving keeps "reduction" and the down arrow.

**What you pay for today.** The monthly build-up has three bars when a quote lookback is set. Full lookback is the fetched year, split by tier, as billed cost. The middle bar is the quote-window usage total and is not split by tier. Serverless at list is the estimator at that window. The year bar is labeled Full lookback.

**Report.** Consolidation headings are not numbered. Each heading is the title of that section. Appendix A and Appendix B are one document, `serverless_consolidation_analysis_appendix`, in the run folder. The consolidation PDFs do not repeat them. Appendix A holds the input arithmetic, the metered-rate tables, the search-power chart when Search was estimated, and the quote integrity score. Appendix B lists each calculated value with its formula, the inputs used, and the result already on the full-retention bulk quote. A row is omitted when that value was not calculated. Sheet dollars on Appendix B stay read-backs. Omit the Monthly search-power estimate when `search_power` is absent. Search-power dollars stay at list. Do not price the Observability store as Search. Fixed overhead in the report is the active deployments on the quote window, as a share of their ECU. The full-lookback overhead includes deployments with no bill in the latest month, so the two figures differ. The smallest clusters' ECU is their whole bill. Their fixed overhead is a separate figure, and the merge saving is a quarter of their bill. Bar charts have a top face and a side face. The usage chart under “What if data is kept longer, or the fleet is busier” is full width. Consolidation type is larger than the account report.

**Raw bulk ingest page.** Required on every diagnostic consolidation PDF, directly after "Where ECH spend sits". It is titled "Raw bulk ingest by deployment" and lists each sized deployment: bundle GB/day (Σ write-index `bulk × 86,400 ÷ write_phase_sec`), quoted GB/day (the same figure on a diagnostic run; a pace factor applies only to the K360 backup), share of the fleet, stored GB, retention days, uptime days, and days in store (stored GB ÷ bundle GB/day, indicative because stored GB is compressed and bulk is not). A by-solution table and a Calculation table follow, with every step and this account's numbers. A node up under 2 days is shaded. The deployment count on this page is the cover count: a serverless project has no bundle and no ECH bill, so it is not a row and is not counted by solution. An active deployment with no bundle gets its own row, marked `no bundle`, and adds no ingest; only a deployment whose bundle measured zero bulk is left to the count under the table. The chart's heading carries the fleet total, and it is the table's Total row. Do not read it as a price: the estimator read-back stays the dollar. Appendix B carries the same formulas under "Raw bulk ingest". Say in chat when the top four deployments are most of the bulk, or when days in store sits far below retention.

**Serverless cost per cluster.** Required on the consolidation PDF when `deployment_plan` has rows, directly after the deployment-count page and before "Where ECH spend sits" (brief: `per_cluster_plan`). One row per cluster, from the Ceiling (each cluster its own project) down every step to the Floor. A cluster in a packed project shows its share of that project's price by bulk GB/day, marked "(of N)", and each column adds up to that step's bar. A cluster whose own project is $10/mo or less at the ceiling is grey. A cluster with a diagnostic bundle that measured no bulk is not sized (grey, "not sized") and takes no share of a packed project. An active cluster with no bundle is flagged "missing diagnostic" and is not sized. A fleet over 36 clusters folds its smallest into one row.

**Deployment-count page.** Required on the canvas when `deployment_plan` has rows, and already printed on the consolidation PDF after the cover. Draw every bar in `deployment_plan`, in order: `label`, `projects`, `monthly`. The count varies. The ceiling is the cover count: one serverless project per deployment that billed in the quote window (the last 90 days of complete billing by default), aligned to that deployment's feature. The cover count and the ceiling are the same deployments. The floor is one project per feature that exists in each region (Observability, Search, or Security). Do not invent a project for a region and feature with no deployments, and do not merge features or regions. Under the chart, name each floor project whose projected sizing is $10/mo or less, with that amount. Those projects stay in the floor count. The estimate sheets are the floor minus that list. An estimate sheet is written only when the projected sizing is more than $10/mo. Each later bar is round(previous × 0.75). round is half-to-even. If that round does not decrease, subtract 1. A result at or under the floor is the floor, and the series stops. Labels are Ceiling, −25% on each middle step, and Floor. Search on a bar is the performant estimator for that project. A Search project with no performant total leaves the bars unpriced. Observability is the D38 read-back. Security is the E74 read-back, and only when E73 is 0. The Observability headline is reused only when the ceiling is already one project. A floor of 1 reached by cutting is priced as that packed group. Appendix B writes that arithmetic with the prior count filled in. Draw `savings.ech_list_mo`, the ECH billed cost, as an ECH bar on every step, beside serverless at list. The figure under the project count is that ECH bill minus serverless at list. Do not reprice the bars. An empty `deployment_plan` means the page was not priced: say so, and do not draw stand-in bars. Each Search project is priced on its measured store.

Confirm the gates from the brief. Do not open the sheet.
- Observability: D38 only when `estimators.observability.echo_gate.accepted` is true. A miss leaves Observability out. The cells on that estimator are what was written.
- Security: quoted only when E73 is 0 and E74 holds nothing beyond ingest, retention, and support (`readback.other_addons_monthly` is 0). `readback.steady_basis` says whether the monthly is month 12 (E74) or month 36; give that when retention is above 12 months.
- Observability split: `estimators.observability.cells` G19 is measured logs plus traces and G20 is measured TSDS metrics, both as monthly GB, and G12 is the metrics month. `readback.echo_gb_day` is the GB/day the sheet priced; `echo_gate.accepted` says it matched what was written. Security has the same `echo_gate`, on G5. Say when the sizing note reports `assumed 90/10`, which means the bundles carried no split.
- Rate window: if `diagnostics_coverage.bulk_short_window_gb_day` is a large part of `bulk_gb_day`, say that much of the rate was measured over less than a day. `bulk_fallback_gb_day` is the part rated without an ILM write phase. A blank, unreadable, or non-zero E73 leaves Security out. A region that was never sized is a missing sheet. No workload skips Security.
- Search-power profiles stay off the quote total, and the Appendix A chart is omitted when `search_power` is absent. Appendix B is in `serverless_consolidation_analysis_appendix` and uses the full-retention bulk quote. A metered row with `at_half_dollar` true is the $0.50 row.
- Template layout: before a cell is written, the run reads the label beside every cell it uses and the sheet's version. A moved row, a blank label, or a version older than Observability v1.22 or Security v2.6 stops the whole run with the cell named, and no quote is written. Report that message as is. A newer version with every label in place is accepted and marked `template_newer_than_validated` on that estimator.
- Unrated ingest: if `diagnostics_coverage.unrated.indices` is above zero, say how many GB of store and what share sit in indices that took bulk writes and have no rate, and name the largest deployments. Those indices are not a data stream, a write alias, or an ILM rollover, or their write index has no write phase. Their ingest is not in bulk GB/day, so say the estimate can sit below the real rate. The `Rated ingest` integrity check is flagged above 5% of local store.
- `ech_scope`: say which scope ran, `in_comparison_mo` against `window_mo`, and name the largest rows in `unpriced` with their reason and `ecu_mo`. `priced_share_pct` under `min_priced_ecu_pct` fails integrity. A deployment's part of the window is its month's cost ÷ the org's daily total for that month, because K360 bills per deployment by month.
- Retention blend: `diagnostics_coverage.retention_blended_share` above 0.10 means that share of local store has no delete policy and no data stream retention. It is taken at its own age, which is how long it has been kept so far, so say the month is a floor for it. A row's `retention_basis` is `policy`, `blended` or `observed`.
- Restart flag: `diagnostics_coverage.bulk_restart_gb_day` is what the bulk rate would add if write indices whose primary shards restarted or moved were spread over their counter's own age. It is a flag, not a correction: the quote keeps esdiag's figure. Say so when it is more than 5% of `bulk_gb_day`, and name the largest in `bulk_restart_deployments`.
- Estimator monotone: a step of the deployment-count plan that costs more than the step before it (by more than 2% and $5) fails the quote. The read-backs are still the dollars. Say which steps, and that an estimator total did not fall as projects merged.
- Sheet echo: the tolerance is 0.1% of the written GB/day, at least 0.02, and every regional sheet is scored beside the fleet sheets.
- `integrity`: give the score, whether it passed, and every check in `failed`. It passes only when every scored check passes: one check in `failed` means `passed` is false, whatever the score. Say so, and do not present a failed quote as verified. It scores the written inputs, the sheet echo, and the published totals. It is not a serverless bill.
- If `diagnostics_coverage.inactive_excluded` is above zero, say how many deployments had no bill in the quote window (`diagnostics_coverage.window_days`, 90 by default). Page 1 counts that roster. It does not count a partial month. If `snapshot_gb` is above zero, say how many searchable-snapshot GB were left out. If `k360_fallback` is above zero, those active deployments had no bundle. They add no ingest and no stored GB, unless `unmeasured_mode` is `k360`: then `k360_priced` lists the ones priced from K360 stored GB, and that part of the estimate is not measured. If `retention_unmeasured` is non-empty, name those deployments.
- Regional dollars are one mode. When a solution spans regions, the headline is the sum of the regional read-backs and there is no second fleet-wide sheet. Each estimator name contains the region it was scoped to. A single-region solution is one sheet, and that name still contains its region. A rejected region leaves that whole solution out. A missing regional read-back leaves that solution out. A stored-GB split is used only when the fleet total is already a quotable read-back. Security stays in a regional quote only when E74 is more than $10.

## Further analysis (only when asked)
A 2–5 project pack, per-deployment prices, or a gap against K360 stored-GB pricing. The K360 backup is a different quantity. Compare it only in a gap section. Do not blend the two into one quote.

```bash
python <skill>/scripts/diag_inputs.py \
  --diags-json serverless_analyzer/diag_artifacts/<org_id>_diags_<date>/sizing_from_diags.json \
  --projects 1,2,3,4,5 --each
```

When the user sets a retention month, pass `--retention-months N` on the consolidation command and keep bulk measured.
